# Business Plugin Reference Skeleton

This directory documents the reusable starting point for a YushuOS business plugin. The executable Task 0.2.0 plugin remains the reference implementation; this skeleton does not duplicate its domain schema or Core ledger code.

## Compatibility

Target Core 0.3.1 (`yushuos-core >=0.3.1,<0.4`), Python 3.11 or newer, Contract v3, and the `json-stdio-v2` runner. The current plugin profile for recoverable local writes is `operation_support: local_commit_v1`.

Read [`../docs/BUSINESS-PLUGIN-AUTHOR-GUIDE.en.md`](../docs/BUSINESS-PLUGIN-AUTHOR-GUIDE.en.md) before creating a plugin. For Task-specific behavior, use [`../docs/SPEC-SOURCE.md`](../docs/SPEC-SOURCE.md) and the actual Task sources: [`contracts.py`](../src/yushuos_task/contracts.py), [`plugin.py`](../src/yushuos_task/plugin.py), [`domain.py`](../src/yushuos_task/domain.py), and [`storage.py`](../src/yushuos_task/storage.py). Copy the process and invariants that apply to your domain; do not copy Task's business tables without a domain-level reason.

## Suggested package layout

```text
plugin/
  plugin.yaml             # generated or validated from the authoritative contract
  run.py                  # one-envelope JSON stdio entry point
  plugin.lock.json        # generated by Core 0.3.1 lock-plugin
  src/
    <package>/            # the verified package installed and run by Core
      contracts.py        # capability schemas and fixtures
      domain.py            # pure validation and state transitions
      storage.py           # domain database, proof, snapshot, migrations
      plugin.py            # Core envelope adapter
tests/
  fixtures/
  unit/
  integration/
```

Core owns its operation ledger. A business plugin owns only its domain database and local commit proof; it must not ship a second claim/receipt/outbox/event ledger. Keep packaging dependencies and business data out of `plugin/`.

## Local write protocol

For each `internal_write` capability, use this sequence:

1. Let Core validate the current capability, permission, resource scope, provider pin, and request schema.
2. Parse the envelope with `PluginContext.from_envelope()` and construct one immutable SDK `Request`.
3. Use Core's bound `fingerprint_for_scheme(request, scheme)` profile and call `StateStore.claim(request)` before the domain write.
4. Commit the domain fact, idempotency proof, original result snapshot, and safe event intents together in one domain-database transaction.
5. Call `StateStore.record_with_events(result, context, emissions)` for a known normal result; return `unknown` if the domain commit exists but the Core receipt/outbox commit cannot be confirmed.
6. Return only after the result has passed the output contract.

The `local_commit_v1` runner actions have separate jobs:

| Action | Contract |
| --- | --- |
| `invoke` | First authorized attempt. Claim the original request ID, then write the domain fact and proof atomically. |
| `recover` | Only explicit `resume --host-mode execute` starts recovery. Read the original proof; if present, call `StateStore.reconcile_confirmed(request, result, context, emissions)`. If absent, return unknown and do not repeat the domain write. |
| `replay` | Core rechecks current permission, resource, capability, and original provider before dispatch. Return the saved result without a business write, marker write, or expiry purge. |

Core retains the original provider ID/version/digest, request intent, project, and trace in the operation context. On recover or replay, use this Core-bound identity. Provider drift fails closed. A proof from another request, operation, store, project, provider version, or provider digest must not be reused.

For the versioned request fingerprint, `jcs-operation-v1` hashes RFC 8785 JCS for `{capability, fields, target}` only. Core separately binds `intent` and top-level `project_ref`. `StateStore.claim(request)` reads the scheme from that Core binding; do not select a scheme by inspecting a digest or silently fall back to a legacy hash.

## Receipts, events, and private data

Core receipts store minimal operation status and request identity; Core outbox events carry only declared event types and safe resource references. Keep business fields, result snapshots, and recovery proof in the domain store. An event emission should be limited to its declared type and safe references.

`changed=false` creates no event intent. A query or preview does not claim, create the business database, mutate a version or timestamp, purge expired result bodies, or emit an event. Core handles preview for local writes before starting the runner.

Task's result snapshots expire logically 180 days after commit. Query, preview, replay, and recovery do not expose an expired body. The next genuine authorized write physically clears expired snapshots; if no such write happens, expired bytes may remain in the database file. Report the committed operation as `succeeded` with `operation_status: committed`, `result_state: expired`, `code: task.result_expired`, `task_id`, and `original_request_id`; omit `task` and `changed`.

The Task event recovery marker is private synchronization metadata, not the authority for a business outcome. If a process stops after the Core receipt/outbox commit but before updating this marker, it may remain `pending`; the Core ledger is authoritative. Keep replay read-only and do not purge or repair markers in replay.

## Contract and verification checklist

- Declare only implemented capabilities, explicit permissions, resource scopes, and emitted event types.
- Keep nullable JSON types explicit, such as `type: [string, "null"]`; YAML `null` is not a type name.
- Use an explicit field allowlist for update operations and `expected_version` for every mutation.
- Make normal, preview, and expired result shapes distinguishable and validate expired output without inventing missing business data.
- Test request identity conflicts, no-op behavior, concurrent version conflicts, provider drift, permission revocation, resource mismatch, all crash windows, and Core-ledger privacy.
- Run the real Core 0.3.1 runner in an isolated temporary configuration and retain the exact commands and outcomes in the release report.

Core API signatures and runner semantics are defined by `yushuos-core 0.3.1/docs/en/PLUGINS.md` and `yushuos-core 0.3.1/docs/zh-CN/PLUGINS.md`; verify changes against the installed Core version.
